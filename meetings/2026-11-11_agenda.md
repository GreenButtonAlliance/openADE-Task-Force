## CMD Mock Service Server (CMDCertification) Releases 1.0.0 and 1.0.1
* Release overview
  * 1.0.0 released October 12, 2026: the first tagged release, and the first whose deployed jar is the released file
  * 1.0.1 released October 29, 2026: documentation and deployment runbook only, with no code or runtime configuration changes
  * Both are built on Spring Boot 3.2.3 and Java 17
  * Versions follow semantic versioning, with the same rules as the SoapUI Application
    - Major: the SoapUI Application must adapt, or what a Data Custodian must do to pass changes
    - Minor: adds behavior that existing callers can ignore
    - Patch: fixes only


* Release 1.0.0 (summary; reviewed at the October 14 meeting)
  * Added
    - The notification endpoint refuses any POST that is not from the Data Custodian under test, or that arrives when no run is in progress
      + Before this, a production utility had been posting into the single notification slot, and the failures were blamed on the utility under test
    - /Admin/EndTestRun clears a run's state, including the Data Custodian's credentials, at the end of every run
    - The build version is logged at the start and end of every run
    - /Admin/GetTokenResponse relays the custodian's token-response headers, when present
      + Date, Content-Type, Cache-Control, and Pragma, as X-DC-* headers, plus X-DC-Headers-Relayed
      + The SoapUI Application uses the relayed Date to check expires_at and authorizedPeriod.start
    - /Admin/OAuthCodeReceivedValue reports how long ago the authorization code arrived
      + Reported as X-Code-Age-Ms, a duration on the platform's monotonic clock and never a timestamp
      + The SoapUI Application does not use it yet
  * Changed
    - Every OAuth parameter is form-encoded, including the HTTP Basic credential
    - The OAuth 'state' parameter is generated for each authorization request instead of being a compile-time constant
      + Operators must not refresh or go back on the callback page, because a replay is now recorded as an error
    - Spring Actuator exposes only health and info
      + Previously, include=* exposed a heap dump holding the TLS private key and keystore password, plus log files holding bearer tokens
    - Notifications are sent as application/xml;charset=UTF-8 and carry no credential
    - The deployed jar carries no configuration; TLS settings are in env.properties
    - The build fails if env.properties would be packaged into the jar
    - Credentials are masked in CMDCerts.log by default: [masked, length=N, fp=xxxxxxxx]
      + This is the same format the SoapUI Application uses, so the two logs can be matched by fingerprint
      + The cmdcert.log.full-token and cmdcert.log.full-credential flags log credentials in clear for diagnostic work
  * Removed
    - The /Admin/SetEncodeScope and /Admin/GetEncodeScope endpoints
    - The committed keystore
    - The Dockerfile and Docker workflow; the platform is released only as private GitHub releases
  * Fixed
    - OAuth callback errors no longer cause a Tomcat 400, and result pages no longer echo values unescaped (an XSS fix)
  * Known issues
    - /Admin/* endpoints are not authenticated; planned for 2.0.0
    - The wildcard TLS private key is in git history and backs the certificate in use; rotating the certificate is what closes this
    - Logs written by earlier builds, or with a full-logging flag on, contain credentials in clear
    - Only one test run at a time is supported


* Release 1.0.1
  * Changed (deployment runbook)
    - The application starts with umask 077, so the logs it writes, which can hold credentials, are readable only by their owner
    - A one-time step restricts existing logs, keystores, private keys, env.properties, and evidence extracts to owner-only access
    - The runbook's monitoring view follows the correct output log
    - The cmd-start, cmd-stop, and cmd-check aliases are documented as systemd-only
  * Fixed
    - Corrections to the 1.0.0 CHANGELOG entry
  * Redeploying is optional; the runbook changes apply to the 1.0.0 jar already on the instance

## CMD Certification Platform (SoapUI Application) Release 4.0.0
* Release overview
  * Released October 30, 2026; tests NAESB REQ.21 (ESPI) v3.3
  * The release number is no longer tied to the NAESB version; each release states which NAESB version it tests
  * Now uses a formal GitHub CI/CD pipeline and release management
    - Release candidates (rc.1 through rc.7) were each regression-tested before the final tag
  * A CHANGELOG.md file has been created to track changes in the software
* Impact for Data Custodians
  * This is a **major** release: it changes what a Data Custodian must do to pass certification
    - Every OAuth request value, including the HTTP Basic credential, must be accepted form-encoded
    - The negative token requests now send the request their names describe, so earlier PASS results for them did not test the stated condition
  * New conformance checks a Data Custodian must now pass
    - One new Authorization for each access token, and each Authorization must match the token response that created it
    - A refused resource request (401 or 403) must carry a correct Bearer WWW-Authenticate challenge
    - ESPI resource requests now send Accept: application/atom+xml
    - The identifiers in a token response's authorizationURI, resourceURI, and customerResourceURI must be distinct
  * Deferred CMD Certification: GBA may agree to temporarily relax specific requirements for a Data Custodian
    - Four switches, all enforced by default: deferAuthorizationPerToken, deferResourceIdentity, deferAcceptAtomXml, deferWwwAuthenticate
    - A deferred check still runs and reports a DEFERRED WARNING instead of a FAIL
    - Every use is shown at the top of the ScriptLog and the Results Summary
    - A deferral expires one year after the custodian's first deferred Certification run with no FAIL; re-runs never renew it
* Added
  * /Admin/EndTestRun is called at the end of every run, so the mock service server clears the run's state and credentials
  * The SoapUI Application and mock service server build versions are logged at the start and end of every run, and recorded in every report
  * The ScriptLog records each token response as one masked [TOKEN-RESPONSE] record
    - It includes the custodian's token-response headers relayed by /Admin/GetTokenResponse: Date, Content-Type, Cache-Control, and Pragma (X-DC-* headers)
  * An Authorization register tracks every Authorization issued during a run and checks it against its token response and the Authorization feed
  * The WWW-Authenticate challenge is checked on every refused resource request
  * Accept: application/atom+xml is sent on every ESPI resource request
  * A token response's identifiers must be distinct
  * The ScriptLog is written to a per-run file as the run proceeds, instead of being copied from SoapUI's 1000-entry log tab
  * IntervalBlock times are shown in the customer's local time
  * Leftover browser windows are swept at run start and end, with an operator dialog when a run does not start clean
  * A second, overlapping start of a test suite is refused
  * An empty or wrong notification is shown to the operator before it is recorded
  * Tools: a regression comparator and an offline notification-validator test
  * The Deferred CMD Certification switches described above
* Changed
  * Every OAuth request value is form-encoded
  * Credentials are masked in the ScriptLog by default
  * OAD016/OAD036 require the applicant to revoke the Authorization; waiting for it to expire no longer counts
  * A failed refusal check fails the step, not the whole test case, so cleanup still runs
  * A wrong-class token may be refused with either 401 or 403
  * The readiness probe stops at once on errors that will not resolve with time, and honors Stop
  * The Results Summary records the actual run start and end times
  * The order of Function Blocks in a scope is no longer significant
* Removed
  * OAD003/OAD023 sub-case 5, which had no normative basis; a corrected version will be announced before it is enforced
  * The PEM test keys; the repository no longer carries a private key
  * The three Incremental Scriptlog Save steps, which the per-run ScriptLog replaces
* Fixed
  * The six negative token-request steps sent an empty POST, and negative token requests began with '?'
  * The Results Summary dropped findings when a test case repeated a step label
  * An invalid configuration did not halt the run when published_min or published_max was empty
  * A feed loop could retry without limit and exhaust memory
  * The readiness probe could run to its 900-second timeout on some feeds
  * The authorizedPeriod.start check failed a start just before UTC midnight; it now judges the actual gap
  * Several false FAILs, orphaned Firefox processes, wrong dates, and a JVM-wide time-zone change
* Known issues
  * /Admin/* calls carry no admin token; now planned for 4.2.0
  * The ScriptLog contains credentials when logFullCredential is set; it is a proprietary record and must not be shared
  * A stalled Data Custodian response has no timeout of its own and can hang a run
  * A test case whose only FAIL is a recorded finding shows green in the SoapUI IDE; the Results Summary is the verdict


## CMD Certification Platform (SoapUI Application) Release 4.1.0
* Release overview
  * Released November 3, 2026; tests NAESB REQ.21 (ESPI) v3.3
  * Regression-tested with CMD Mock Service Server 1.0.1 against two Data Custodians
    - Release gate: one Data Custodian passed all 52 cases; the other's failing set did not change

* Impact for Data Custodians
  * This is a **minor** release: some verdicts change, but what a Data Custodian must do to pass does not
  * Two changes apply to every Data Custodian
    - A NOT EVALUATED result now follows its cause (details under Changed)
    - An empty Authorization is reported as its own finding, [Authorization content]
  * Three deferral changes reach a Data Custodian only under a GBA decision
* Added
  * Two new Deferred CMD Certification switches, both enforced by default, for client_credentials Authorizations (the Authorizations named by registration and client access tokens)
    - deferClientCredentialsAuthorization: the self href and the checks that the entry matches its token response
    - deferClientCredentialsAuthorizationEntry: an empty Authorization, or one missing from the Authorization feed
    - Neither switch ever defers a customer Authorization or a token-response check
* Changed
  * An empty Authorization is reported as [Authorization content] instead of [self href]
    - [self href] now means only an entry with content that has no matching rel="self" link
  * A NOT EVALUATED result now follows its cause
    - If the Data Custodian caused it (for example, an Authorization feed answered with an unexpected status or a non-Atom body, or a token response with no expires_in), it is a FAIL
      + The FAIL names the status, URL, and response Date, and is never retried into a PASS
    - If the SoapUI Application, the mock service server, or the run itself caused it, the session is marked INVALID
      + An INVALID session is flagged in the Results Summary and never starts a deferral year
    - Before this release, an HTTP 500 from the feed left checks NOT EVALUATED, so a case could pass without the check being made
  * deferAuthorizationPerToken also defers an HTTP 5xx from the Authorization feed read right after a revocation
    - A 4xx, a non-Atom body, and any finding on a feed that answers 200 are not deferred
    - When more than one switch could defer a finding, the first one that is on defers it
  * Every finding about the revoked Authorization says it is expected in the feed with status 0 (Revoked)
